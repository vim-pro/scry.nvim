1. INTRODUCTION                                            *scry-introduction*

OPERATORS, ONE NOUN UP.

Vim's bargain is operators x text objects. `d2w`, `ci"`, `>ap` — small
orthogonal verbs applied to precisely addressed nouns, repeatable with `.`,
fannable with `:g`. That grammar is why vim outlived every editor that set
out to replace it.

conjurer.nvim ported the grammar to generated edits: `~{motion}` is an
operator whose effect is REWRITE THIS REGION TOWARD AN INTENT. Same verbs,
same nouns, a new effect.

scry raises the noun. Not a region in a file — a CAPABILITY. The glass is
not a report you read; it is the noun-space you aim at.

Put the cursor on `Tailor a checklist to your own situation`, press `~`,
say what you want. The change lands across compile.ts, c/[slug].astro,
copy.astro and c/index.astro. Four files, one intent, and you never opened
one. `.` repeats it on the next feature. `:g/^feature.*export/normal ~`
fans it across every capability that matches. Nothing new to learn — you
know the grammar already; scry gives it a bigger noun. See |scry-compose|.

Adding a capability is the same verb, because an address exists before the
file does: `route print` names src/pages/print.astro whether or not
anything is there yet (|scry-kinds|). Write the feature you want with the
members it should have and cast — absent members are files to create.

EVERYTHING ELSE HERE EXISTS TO MAKE THAT ADDRESS REAL. The checks say
whether what you asked for actually landed. The kinds say where a member's
file lives. Divergence says what has no address yet. None of that is the
point; the point is that a capability has an address you can put a cursor
on, and the rest is what keeps the address from lying.

So the checks are a means. They keep the description honest while you write
it — you find out you meant something slightly different from what you
typed, which is the whole reason to type it. What scry cannot do is recover
your understanding for you: a program's theory lives in the people who
built it, and this narrows the drift rather than storing the theory. See
|scry-honesty| for what each verdict does and does not assert.

Three tools, three jobs: the glass is where you work (scry.nvim), the
conjurer types (conjurer.nvim), and the list is where changes get reviewed
(quickfix-pro).

2. THE GLASS                                                      *scry-glass*

|:Scry| opens `scry://glass` — one editable buffer holding your whole model,
with verdicts rendered beside each claim as virtual text. The verdicts are
COMPUTED, never stored: the buffer's text is your beliefs, and everything
after it is scry's answer.

Editing the model is the primary gesture. `:write` saves it — and routes
never-claims to the holdout file (|scry-holdout|), announcing where they
went. Every render carries a header:
>
    scry · 9 features · 5 done · 2 building · 1 broken · 1 to do   checked 40s ago (files on disk)
          21 claims · 15 backed · 3 missing · 1 violated · 2 unchecked · 4 untouched
<
Features lead, because the question a reader arrives with is what the
product does — not how many subfunctions resolved. Claim numbers are the
evidence behind that first line, so they come second. Reading them first is
the altitude mistake the whole map exists to avoid.

"files on disk" is not decoration: scry reads saved files, so an unwritten
buffer is invisible to it. A verdict is always presented with when it was
computed and against what.

`backed + missing + violated + unchecked` always equals the claim count. The
unchecked column appears only when it is non-zero, and it is there so that
"0 missing · 0 violated" can never be read as a clean bill of health for
claims no engine ever answered. See |scry-debt|.

Each feature carries the state its own evidence adds up to — nothing here is
authored:

    ✓ done             every claim holds, and you have read this
    ✗ broken (1 of 5)  a claim regressed; outranks everything else
    – unread (5 of 5)  every claim holds and nobody has read it
    ◐ 2 of 5           real progress: some evidence holds
    ✗ not yet          nothing holds — the state you create on purpose
    – unchecked (n)    nothing has answered yet; NOT progress
    – no evidence yet  named, with nothing checkable under it

`– unread` exists because evidence and engagement are different questions,
and a feature can pass the first while failing the second entirely. That is
the state a drafting pass leaves behind (|scry-drafting|), and also the state
a map you have just cloned is in — the trail is per-machine and unversioned,
so someone else's understanding does not arrive with their file. Calling
either one `✓ done` would put a finished product on the line you scan.

One owned claim is enough to make a feature read: the question is whether a
human has been through the description at all, not whether they finished it.
And `unread` displaces `done` only — a half-backed feature nobody has touched
still reads `◐ 2 of 5`, because progress is the more useful reading and is not
a claim of completion.

3. THE MAP                                                          *scry-map*

The map is plain text, versioned with the code it describes (default
`.scry/map.scry`). Line-oriented and deliberately dull:
>
    feature a user can reset their password
      Requests a link by email. The link expires in 15 minutes and burns
      on use.

      contains
        lua/auth/reset.lua:request_reset
        lua/auth/reset.lua:consume_link
      calls
        mailer::send
      never
        token.*log
      exercises
        tests/reset_spec.lua:the link burns on use
<
- `feature <statement>` starts a feature. See |scry-altitude| for what
  belongs on that line — it is the one judgment the map asks of you.
- `contains`, `calls`, `never`, `exercises` open a claim block; claims are
  indented four spaces and are that feature's EVIDENCE, never its peers.
- **Everything else is prose.** There are no parse errors: a line is a claim
  or it is prose, preserved verbatim, never checked, never marked. Write as
  much explanation as you like — the sentences carry the theory, the claims
  carry the check.

Indentation is the grammar; vertical space is layout. A blank line does NOT
close a claim block — you can paragraph a long list of prohibitions and every
one of them is still a claim. Only a dedented non-blank line ends a block.
(This matters more than it looks: a blank treated as a terminator would demote
the rest of a `never` block to prose, which both stops checking those patterns
and routes them into the repository on the next |:write|.)

                                                                 *scry-reach*
REACH — WHAT A DEFINITION ACTUALLY TOUCHES ~

A feature's members are its ENTRY POINTS. The code behind them is not
something anyone should have to list, and listing it is what made a map of a
real project run to eighty-six members.

WHAT REACH ANSWERS is one direction of two, and scry uses only that one:
everything a feature's entry points REACH, transitively, which is its
footprint. The opposite question — everything that binds to a definition,
"who uses this" — is a real question and a different one, and scry does not
ask it. An entry point nobody calls has no callers and a large footprint,
and that is exactly what an entry point is.

IT RUNS BY ITSELF. Reach is computed for the whole map in the background
whenever the glass checks, and cached with a fingerprint so a second look
costs nothing and a stale answer is discarded rather than trusted. It used
to be a command run one feature at a time, which meant that for anyone who
did not know to make that gesture the unclaimed count was computed as
though reach did not exist. Until it is in, the header says so: `48
unclaimed files (reach pending)`, or `(no reach)` where no engine can
answer.

THE FOOTPRINT IS WHY THIS EXISTS. A file a feature's entry points genuinely
reach is described by that feature whether or not anyone typed its name, so
|scry-divergence| counts it as claimed. On a four-file fixture with one
named entry point, the unclaimed list goes from three files to one — and the
one left is the file nothing reaches. Making someone name the other two by
hand is what turned a map of a real project into eighty-six members.

Only a RESOLVED answer is recorded. A name match would quietly excuse every
file that mentions a common word, which is the opposite of what the
unclaimed list is for. The record carries a stamp of the files it was
computed from and is ignored once any of them changes: a stale reach is
worse than none, because it would keep a file off the list on the strength
of a binding that has since been deleted.

THE RESOLVING ITSELF IS NOT SCRY'S. It lives in stackgraphs.nvim, which
answers four questions — what a name binds to, what binds to a definition,
what a file reaches, and the transitive closure of that — and labels every
answer with a fidelity. Scry may never render a stronger word than the one
it was handed. See |stackgraphs| for the contract.

That seam has already paid for itself. The backend behind it was swapped
from an archived stack-graphs CLI to a LANGUAGE SERVER, and nothing in scry
changed — not the map, not the glass, not one of the fourteen specs. It also
widened what reach can answer about: a language server resolves lua, go,
rust and c, which stack graphs never did, so scry's own map is now reachable
by the same machinery as a TypeScript project.

Reach on a def is two passes, and the split is the honesty:

    candidates   ripgrep finds every position that mentions the name.
                 Fast, over-broad, never reported as more than it is.
    resolved     the engine is asked, for each candidate, whether it binds
                 to THIS definition. What survives is reach.

The difference is not small. On a fixture with one real caller and one
unrelated function of the same name, ripgrep reports five positions and the
engine keeps one — and two of the four it drops are a DIFFERENT function
that merely shares a name. That is the question a text search cannot answer
and the reason reach needs an engine at all.

Without one, the first pass still runs and the quickfix title says
`text only`, because a name match is evidence of a mention and nothing
more. Scry says which kind of answer it has every time it gives one.

REACH IS OPTIONAL. Without stackgraphs.nvim installed, every verdict scry
gives still works — kinds are probed by path and grep, `def` by treesitter
— and only the divergence shrink goes away. |:checkhealth|
says so rather than scry failing to load.

    https://github.com/vim-pro/stackgraphs.nvim

A RESOLVER is per language, and |:checkhealth| reports what resolves what.
Either a language server on $PATH — nothing to configure — or a stack-graphs
engine: >

    cargo install tree-sitter-stack-graphs-typescript --features cli \
      --root ~/.local/share/nvim/stackgraphs
<
Engines already installed under ~/.local/share/nvim/scry are still found, so
an existing install does not need redoing. See |stackgraphs-backends| for
which servers are recognized out of the box.

                                                        *scry-reach-limits*
REACH IS NOT UNIFORM, and what follows is what has been measured rather
than what would be tidy.

Every language present is indexed into ONE database, so an import that
crosses from TypeScript into JavaScript can resolve, and on a small fixture
it does. On one real Astro project it does not: an imported name resolves
to its own import binding and the chain stops there instead of continuing
into the `.js` file, so a page that imports four modules reaches none of
them. Why the fixture completes the chain and the project does not is NOT
established. Do not read a confident zero as proof your code has no
dependencies.

A file where NOT ONE identifier resolves is reported unresolved — an
unindexed language, or a grammar that choked — so it is never recorded and
never shrinks |scry-divergence|. That check is weak on purpose and weak in
fact: a file whose identifiers resolve only to itself passes it and still
reaches nothing.

Indexing is the slowest thing scry does, which is why reach is a command
and never part of a check. |:Scry| stays cheap; only a command may be
expensive, the same rule |:ScryExercise| and |:ScryDraft| follow.

                                                                 *scry-kinds*
A MEMBER NAMES A TYPED OBJECT ~

A feature's members say what the product is MADE of, and each carries a
KIND: >

    feature a reader can follow a link someone sent them
      route [slug]
        The run view. #done= carries progress to a friend.
      module src/lib/run.js
      def src/lib/run.js:initChecklist
<
The kind is the difference between a map of the product and a map of the
filesystem. It carries what a bare path never could — how to find one of
these, and what one of these IS — and a member may carry its own one-line
intent, indented under it: what THAT member is for, as against what the
feature is for.

Two kinds need no declaring. `module` needs no parser, since a file is on
disk or it is not, which makes it the one kind that works in every
language; `def` needs a grammar and says so when it has none.

Every other kind is declared by the project, in |scry-project-config|,
because what a product is made of is the most project-shaped fact there is —
routes and endpoints describe a web app, commands describe a plugin, and
neither vocabulary is right for the other: >

    "kinds": {
      "route":    { "path": "src/pages/{name}.astro" },
      "endpoint": { "path": "src/pages/api/{name}.ts" },
      "command":  { "grep": "nvim_create_user_command\\(\"{name}\"" }
    }
<
A MEMBER'S NAME IS EXACTLY THE TEXT THE PROBE SUBSTITUTES, and nothing
else. For `"endpoint": { "path": "src/pages/api/{name}.ts" }` the names are
`compile` and `suggest` — not `/index.json`, which is what the endpoint
means to a person. Scry would paste that in and report
`src/pages/api//index.json.ts` absent: accurate, about a path nobody meant.

|:ScryDraft| settles it by showing rather than telling. It lists the names
of each kind that already exist, taken off disk, so a drafter writes names
of the same shape.

A kind is a name and a way to find one — `path` for a file at a location,
`grep` for a pattern anywhere in the project. `{name}` is the member's name,
escaped for the probe it enters (a route called `[slug]` is a character
class to ripgrep, and unescaped would match the wrong thing). A kind the
project has not declared is PROSE, never a claim: scry has no business
pretending to check something it has no probe for.

Prose and a member are the same shape — `route /a` and `Prose here.` are
both two words at two spaces — so what makes a line a member is that its
kind is one this project has. That is why the parser takes the kinds.

`contains` and `calls` still parse, and always will. `contains` was doing
two jobs and its shape said which: with a symbol a definition, without one a
file. Reading it as `def` and `module` is a renaming, not a
reinterpretation, so no map anyone wrote changes meaning.

Claim targets differ by kind, because the claims differ in kind:

    contains   path:symbol            a definition exists at a location
    contains   path                   that file is part of this feature
    calls      [hint::]symbol         target exists, and this feature
                                      references it
    never      a ripgrep regex        zero matches in the footprint
    exercises  path[:assertion]       that spec passes — see |scry-exercised|

The second `contains` form — a path with no symbol — exists for files that
define nothing a claim could name: a `plugin/` bootstrap, a table of
settings, anything not lua. |scry-divergence| is file-level while footprints
are symbol-derived, so without it such a file gets reported as unclaimed
with no way to claim it, and an accusation you cannot act on is a defect in
the report rather than in your map.

It is the weakest claim in the vocabulary and reads as one:
`✓ present (file)`, never `✓ defined`. Reach for it when
there is no symbol to name — not to cover ground quickly. A map of bare
paths is a list of files, which is the altitude mistake features exist to
prevent.

`never` patterns are raw ripgrep regexes — `vim\.ui\.`, not `vim.ui.*`. No
sugar is applied, because silently mis-escaping a prohibition would be
exactly the kind of quiet overclaim scry exists to avoid.

                                                              *scry-altitude*
ALTITUDE — what belongs on a feature line ~

A feature is a SEA-LEVEL object in Cockburn's sense: one thing a user of
this system can accomplish, named the way they would name it. His three
tests, which transfer almost unchanged:

- Is it one thing, done in one sitting?
- Could you stop when it is finished?
- Does it matter that you can do many of them?

"Log on" fails the third — logging on forty-three times satisfies nothing.
"A user can reset their password" passes all three. The shortest useful
summary of what a system does is the list of its sea-level statements, and
that is exactly what the map's feature lines are for.

Two neighbouring altitudes ruin a map, and the grammar is built to keep
them out:

ABOVE — "the auth system", "billing". These are groupings, not work. They
name a place in the code, and a map of them tells you nothing about what
the product does. This is what the old `# concern` + `files <glob>` header
was, and why it was replaced: a glob is a directory, and a feature is not
a directory.

BELOW — "validate the token", "parse the header". These are subfunctions,
and they are exactly what claims already are. Cockburn's warning is the
one worth memorising: a hundred pages of subfunctions "did not serve
either its writers or readers", and six user-goal statements replaced
them. Claims stay subordinate for that reason.

For a library or a plugin the actor changes but the level does not: the
user is the calling programmer, so `~ip conjures over a paragraph` is sea
level and `parse_sse` is a subfunction. Cockburn calls this design scope.

If you cannot tell which side of the line something falls on, write it
deliberately too high, then deliberately too low, then judge the middle —
Kent Beck's Three Bears. Calibration by contrast works where a rule does
not.

                                                             *scry-reopening*
NAMING A FEATURE TWICE ~

A feature is named once and its members accumulate. Writing the same name
again re-opens that feature and adds to it; it does not start a second
feature with an identical name. Prose may sit between the blocks, and the
stored text is untouched — the map round-trips byte for byte as ever.

This is how a map grows. |:ScryDraft| works through a project a batch at a
time, and a batch whose files serve a feature already written needs a way to
say so; without one its only legal output is a NEW feature, and the map
fragments a file at a time. One pass reached 301 features over 60 files that
way.

Merging is by EXACT name. Deciding that two wordings mean the same thing is
the reader's call, not scry's — near-identical names stay two features until
you make them one.

                                                            *scry-footprint*
FOOTPRINT — derived, never declared ~

A feature's scope is the union of files its located claims name. `def`,
`module` and `exercises` contribute their paths. A declared kind probed by
`path` contributes the file its name expands to — `route c/[slug]` under
`src/pages/{name}.astro` is `src/pages/c/[slug].astro`, the same
substitution read backwards to discover names in the first place. A kind
probed by `grep` contributes nothing, because a pattern can match anywhere
and is not a place; neither is `calls`, which carries a hint, nor `never`.
Nothing declares a footprint, so it cannot drift from the claims it
describes.

A path-probed kind used to contribute nothing either, and the cost was not
cosmetic: divergence never counted those pages as described, so they stayed
on the undescribed worklist and |:ScryDraft| was asked about them on every
pass. Since a claim's identity includes its feature name, each rewording
looked like new work. One run reached 301 features over 60 files before it
was stopped by hand.

An empty footprint is meaningful, not a bug. A feature that locates nothing
yet has nowhere for a prohibition to look, and `never` renders
`– unscoped` rather than quietly searching the whole project and reporting
violations in files the feature does not own.

                                                              *scry-two-axes*
The kinds sit on two axes, and it is worth seeing them that way rather than
as a list of four:

    contains / calls / never    STATIC — a definition node, a text match.
                                Cheap, side-effect-free, recomputed on
                                every check.
    exercises                   DYNAMIC — something was run and it passed.
                                Slow, stateful, and stale the moment you
                                edit.

Structural claims say where things are; an exercised claim says what holds.
Neither is the primary axis. Adding a feature usually wants one of each —
`contains` for the thing existing, `exercises` for it working — and fixing a
bug often wants only the second, since nothing structural changed.

4. VERDICTS                                                    *scry-verdicts*

The glyph never appears alone. The label states what was actually checked:

    ✓ defined              a definition node with that name exists (treesitter)
    ✓ referenced (text)    the token occurs in the feature's files (ripgrep)
    ✓ no matches (rg)      the prohibition found nothing
    ✓ passing (ran 4m ago) that spec exited 0, and nothing it depends on has
                           changed since — the age is part of the verdict
    ✗ absent               the definition (or target) does not exist
    ✗ unreferenced         the target exists, but this feature never mentions it
    ✗ VIOLATED             a prohibition matched — with the evidence line
    ✗ FAILING              that spec exited non-zero — with its output
    ∅ untouched            no work has passed through this claim yet
    – unchecked            no resolver for this language; NOT a pass
    – unrun                nobody has run that spec yet; NOT a pass
    – stale                it passed, but the code has moved since; NOT a pass
    – vacuous?             it passes, and nothing its feature claims exists
                           yet — so it is asserting nothing. NOT a pass

That vocabulary is the honesty mechanism, not decoration. The fidelity of
the evidence travels with the verdict, so the glass cannot render a stronger
word than the engine that produced it. See |scry-honesty| for what each
verdict does and does not assert.

                                                            *scry-divergence*
DIVERGENCE — the code no feature claims ~

Reflexion has three verdicts, and the two above are only the first two.
Convergence is `✓ defined`; absence is `✗ absent`; DIVERGENCE is reality the
map does not account for. Without it a feature list cannot be read honestly:
every feature can be `✓ done` while the map describes a tenth of the
product, and nothing on the page would say so.

Two kinds of file are never counted. |scry-configuration|'s `sources` says
what THIS product is made of, and is yours to draw. Separately, and
categorically, scry omits files no feature could ever claim: pictures,
fonts, media, and lockfiles. An icon has no behavior to describe and a
lockfile records a resolver's arithmetic — the same reasoning that keeps
`.scry/` out of the count, rather than a judgment about your project.

That list is deliberately short. Generated code is still code, content is
still content, and build config is a decision someone made; a reader may
reasonably call any of them product, so scry leaves them in and lets
`sources` settle it.

A file counts as claimed when some feature's footprint names it
(|scry-footprint|). Everything else is unclaimed, and the header says how
many:
>
    scry · 9 features · 9 done · 12 unclaimed files   just checked
<
|:ScryUnclaimed| puts them in the quickfix list, because that is where every
other list of work lives. Each one is a decision: add a claim to the feature
that should own this file, or name the feature nobody wrote down.

Deliberately FILE-level. Enumerating every definition and listing the
unclaimed ones is the obvious implementation and the wrong one — it produces
a list of `chomp`, `clip`, and `stat`, which is the implementation wearing a
product's clothes. "lua/auth/tokens.lua is covered by no feature" is a
sentence you can act on; "`chomp` is unclaimed" is noise.

Two honest limits. A file a feature genuinely uses but never names still
reads as unclaimed — correct, because the map's job is to say what the
product does and silence about a file is silence. And `sources` decides what
counts as claimable at all; empty means everything ripgrep lists, which
respects `.gitignore`. Narrowing it is expected, and having to narrow it a
lot is itself information about the repo.

Narrowing `sources` is also the one move that can make this report lie, so
it is worth being deliberate about. Excluding a test runner or a file of
assertion helpers is honest: they are how the product is built, not what it
does. Excluding product to make the number drop is the same act mechanically
and the opposite act in substance, and nothing here can tell the difference
for you. If a path is arguably product, leave it in and claim it — the
file-level `contains` form exists so that is always possible.

                                                               *scry-scale*
AT SCALE ~

Measured on a twenty-thousand-file project with twelve hundred claims:
parsing the map takes 2ms, divergence 24ms, checking every claim 59ms, the
counts 37ms. Looking is cheap and stays cheap; nothing in the check path is
the thing that fails first.

WHAT FAILS IS THE REPORT. Eighteen thousand eight hundred unclaimed files is
not a list — it is the same wall of detail |scry-altitude| is about, one
level up, and a quickfix window with eighteen thousand rows is a thing you
close rather than a thing you work. |:ScryUnclaimed| groups by directory
until the answer fits in something a reader can hold: `packages/pkg042 —
100 files, nothing claims any of them` is a sentence you can act on. Every
file is still accounted for in the counts, each row jumps to a real file,
and a small project has its files named one by one as before.
|:ScryUnclaimed|! lists every file however many there are.

RE-OPENING, AND WHY IT DOES NOT READ AS REPETITION. A batch whose files
serve a feature already in the map says so by writing that feature's name
again with the new members under it — |scry-reopening|. The parser has
always read those blocks as one feature. The buffer did not: four batches
adding to one capability left four `feature` lines with the same name, so a
map of fourteen was written across twenty-eight headers and read as a page
of duplicates.

Each batch now gathers its re-opened blocks into the features they belong
to as it lands, in the same tick as the splice — so `u` still undoes a
batch as one thing. A member written twice is kept once. A feature written
only once is returned exactly as it was, blank lines and all, because its
layout is yours. |:ScryTidy| does the same on demand, for a map written
before this did it.

AND THE DRAFT IS A BATCH, BUT THE COMMAND IS A PASS. |:ScryDraft| used to
send the whole worklist, which already ran past a five-minute timeout at
seventy-two files and is not a long request at twenty thousand but an
impossible one. So a request takes a bounded number — and since a project
has thousands of files, one request can never be the unit of work. Running
the command a hundred and thirty times is being the loop by hand.

A pass keeps going: each batch issues the next when it lands, and what to
ask about is recomputed from the buffer every time, because a kept draft
CLAIMS what it described and may well have claimed files outside its own
batch. Files come in the order divergence found them, which keeps a
directory's files together, so a batch tends to be one part of the product
rather than a scatter.

IT ENDS on its own when the files run out, and on its own when a batch
describes nothing new — without that rule, a file the model declines to
describe is asked about forever. |:ScryDraftStop| ends it after the batch
in flight, which is left to land because it is already paid for.
|:ConjureCancel| is the other choice: it kills the request, and a failed
request ends the pass.

                                                            *scry-drafting*
DRAFTING THE GAP ~

|:ScryDraft| takes the unclaimed files and asks a conjurer to write features
for them, into the glass, where you read them.

WHAT YOU SEE while it works is two lines and the conjurer narrating between
them. The worklist goes out in the request, not into the buffer: it used to
be the region the model rewrote, so a draft opened by pasting every
undescribed path into the glass — seventy-two file names nobody asked to
read, with the narration buried at the top of them. The model needs that
list. The buffer needs somewhere for the narration to land.

Both lines are prose, so rejecting with `u` leaves nothing behind, and the
starter (|scry-glass|) is cleared on the way in — it is instructions for
someone with no map, and a draft is a map.

This is the scrying itself, and it is the one place a machine writes into the
map, so it is worth being exact about why that is not a contradiction. The
argument for an authored model is that recovered ones are about half right,
and half right is worse than absent because you stop looking. That still
stands. What it does not require is that authoring start from an empty
buffer.

The distinction that carries the weight: A DRAFT IS NOT A BELIEF. A drafted
claim has no ownership trail, so it renders untouched and the header counts
it as untouched — which is the honest reading of a hundred machine-written
claims nobody has read. It is inventory. It becomes a belief when you edit
it, and editing is what records the trail (|scry-ownership|). The machine
does the typing; you do the deciding.

The pass is scoped by divergence rather than by repository, so it drafts
against the gap instead of re-describing the product. That is what keeps each
pass short enough to actually read, and it means the report you ran to find
the gap is the report that closes it.

The glass is the review. A drafted feature wants to be read beside the rest
of the map, with its claims checked and its untouched marker showing, and
none of that survives a diff view — so the draft lands in the buffer, `u`
discards it, and nothing reaches the map file until you |:write|.

Two things a drafting pass will not do. It will not write a `never` block: a
prohibition lands outside the repository, unversioned, and narrows every
future cascade, so one nobody read is worse than none. And it does not
involve the holdout at all — a prohibition is withheld from CODE requests
because a rule the generator was shown proves nothing by being satisfied,
and this request produces map text, so there is no result for a leaked rule
to have been fitted to. Running the tripwire here would look like a
guarantee while guaranteeing nothing, which is worse than saying so.

==============================================================================
5. OWNERSHIP                                                  *scry-ownership*

The ordinary actions of doing the work each record a trail event on the
claim they touch:

    authored     you typed or edited the claim's text in the glass
    conjured     you sent it to the conjurer (|scry-conjure|)
    red / green  its spec failed, then passed, under your |:ScryExercise|
    settled      a claim you conjured came true on your save

A claim is YOURS — and drops its `∅ untouched` marker — when the trail
shows you passed through it: authored, or conjured and it came true. A
machine-drafted claim nobody has engaged with stays marked, which is
exactly what the marker is for: inventory is not understanding.

Every event is keyed to a hash of the claim's text at the moment it was
recorded, so editing a claim resets its trail — mechanically, no hooks.
Trails live outside the repo under `stdpath("state")`, like run results:
facts about what you did on this machine, not something to commit.

A `-- @name date hex` suffix on a claim line parses and is kept as data.

==============================================================================
6. THEORY-DEBT                                                     *scry-debt*

Two separate numbers, never blended into one score:

- **untouched** — claims no work has passed through yet. See
  |scry-ownership|.
- **diverged** — claims that are missing or violated.

A claim is also always in exactly one verdict column — backed, missing,
violated, or **unchecked**. Unchecked collects everything no engine could
answer: no resolver for the language, a parse failure, a resolver error, or
no check having run yet. It is not a pass, so it is counted rather than
omitted; a column that vanished when empty of good news would let the reader
infer safety by subtraction.

The claim count leads every rendering, and that is deliberate: `0 diverged /
3 claims` means your map is THIN, not that your repo is healthy. Until scry
can report code that no claim covers, debt says nothing about unclaimed
code.

`require("scry.debt").statusline()` returns a compact string for your own
statusline: `scry 14c ✓11 ✗2 ∅3`, gaining a `–N` when anything is unchecked; `∅` counts untouched claims.

==============================================================================
7. THE HOLDOUT                                                  *scry-holdout*

A `never` claim is a holdout: it is withheld from the generator and checked
after. That restores independence mechanically. If the model that writes the
code is also shown the prohibition, its output satisfying that prohibition
tells you nothing — it was asked to satisfy it. A prohibition it never saw,
checked afterwards, is real evidence.

This is why prohibitions and positive claims are stored apart. never-claims
live OUTSIDE the repository by default, under `stdpath("state")`, keyed to
the project path. The glass still shows them inline; only storage differs.

Two guarantees, deliberately not conflated:

1. **Withheld from requests** — guaranteed and covered by tests. Everything
   scry hands a conjurer is built from the feature name, the claim's own
   target, and the intent you typed. Feature prose is excluded on purpose:
   prose can restate a prohibition in words no scrubber could catch, so the
   channel is closed rather than filtered.
2. **Hidden from the filesystem** — true for a generator that reads your
   repo; NOT true for one instructed to hunt your filesystem. Independence
   here is against leakage, not against an adversary.

The cost is honest too: out-of-repo prohibitions are per-machine and
unversioned. Setting `holdout_path` to an in-repo file shares them with your
team and gives up guarantee 2 — |:checkhealth| warns when you do.

==============================================================================
8. CONJURING FROM THE GLASS                                     *scry-conjure*

An absent claim is a piece of work. |scry-conjure| on that claim seeds the
quickfix list with the target site and your intent, then hands off to
conjurer's aggregate driver — which owns the casting and the per-site review
(see |conjurer-aggregate|). scry never conjures anything itself.

When you save a file the conjure seeded, scry re-checks: the withheld
prohibitions run against the new code, and the claim that started the work
re-checks too. So the loop closes visibly — `✗ absent` becomes `✓ defined`,
and because you conjured it and it came true, it is yours.

Saving is the trigger because ripgrep reads disk. Unwritten changes are
invisible to scry, and the header says so.

A claim may name a file that does not exist yet — that is the normal state of
work not yet done. Seeding creates it (and its parent directories), because
conjurer rewrites a region of a buffer and needs one to rewrite.

Two v0 limits worth knowing. The seeded entry points at the target file's
first line — scry knows which file should define the symbol, not where in it
the definition belongs, so the model decides placement and the conjurer's
review is where you check it. And `calls` and `never` claims cannot be conjured:
neither has a single obvious site to seed, and guessing one would be worse
than refusing.

------------------------------------------------------------------------------
INDEPENDENCE OF THE CHECK                                  *scry-independence*

`contains` and `exercises` can both be conjured, and the ORDER is the
mechanism, not a convention:
>
    1.  :Conjure on the absent `exercises` claim   → conjures the CHECK
    2.  read it                                         ← the judgment act
    3.  :ScryExercise                                        → it must be RED
    4.  :Conjure on the absent `contains` claim    → conjures the CODE
    5.  :ScryExercise                                        → green, and the
                                                          holdout re-checks
    6.  it is yours — you conjured it and it came true
<
Why in that order. If the check and the code are both generated from the same
claim, they are not independent — they are two samples from one generator
reading one sentence, so they share its misreadings. Both can be confidently
wrong in the same direction and the suite is green. When a person wrote the
code, their reading of the claim was an independent sample; remove that and
`✓ passing` decays into *the generator was self-consistent*.

So two things restore it, and both are enforced rather than advised:

**The spec is withheld from the code request.** Conjuring a `contains` claim
adds every spec path in that feature to the tripwire, exactly as it adds the
feature's prohibitions. An intent that names the test is refused. Code written
while looking at the test is code written to pass the test, which is the one
thing an acceptance check must not be written to do.

The limit is stated plainly: this is request-level withholding only. A
never-pattern can live outside the repository; a spec has to be in the tree to
run, so a generator instructed to read your repository will find it. Same
distinction as |scry-holdout|, and it is kept sharp for the same reason.

**A check written before the code must fail.** One that passes against a
feature nobody has built is asserting nothing — the commonest way a conjured
test is worthless, and invisible from inside the run, since the process exits
0 either way. So a check downgrades a passing `exercises` claim to
`– vacuous?` when every `contains` claim in its feature is still absent. It is
deliberately conservative: a half-built feature has plenty for a spec to
legitimately exercise, and a false alarm would teach you to ignore the real
one.

Step 2 is the one no mechanism can do for you. If almost nothing is written
by hand, the artifact you must actually read is the check — it is short,
declarative, and sits at the altitude of the claim, which makes "yes, that is
what I meant" a performable act in a way that reading the implementation is
not.

==============================================================================
9. EXERCISED CLAIMS                                           *scry-exercised*

An `exercises` claim names a spec, optionally with an assertion label:
>
    # the aggregate driver
      files lua/conjurer/quickfix.lua

      exercises
        tests/aggregate_spec.lua
        tests/aggregate_spec.lua:driven casts never open a review tab
<
**Checking never runs anything.** |:Scry| and |:ScryCheck| read what the last
|:ScryExercise| recorded; only |:ScryExercise| executes. That separation is deliberate.
Every other verdict is a static read — cheap, repeatable, harmless to
recompute. Running a suite is slow, has side effects, and can hang, and a
glass that shelled out to your test suite whenever you opened it is a glass
you would stop opening.

The price is staleness, and staleness is the whole danger of this evidence
class: `✓ passing` from before your last edit looks like the strongest thing
scry renders and is the easiest one to be wrong. So a recorded run is
reported as a pass only while nothing it depended on has moved. Each run
fingerprints the feature's files and the spec as it starts; a later check
compares. Any difference and the verdict degrades to `– stale`, which lands
in the unchecked column, where an unanswered claim belongs.

Fingerprints rather than timestamps, because mtime granularity is one second
and "edit, then run" finishes inside a single tick — a clock comparison would
call every fresh run stale forever.

Two claims on one spec are one execution, and its recorded dependencies cover
every feature that exercises it.

=========================================================================                                                              *scry-mappings*
MOVING AROUND ~

The glass is a normal, writable buffer, so it keeps every editing key it
has. One mapping is added, and it means "take me to what this line is
about":

    <Tab>       expand or collapse the feature under the cursor
    <CR>        on a CLAIM, open the code it points at
                on a FEATURE line, the same as <Tab>

WHERE A CLAIM TAKES YOU, in order. Evidence first, always: if the last check
found a line for this claim, that is somewhere an engine actually looked, so
it is the truest destination scry has. A `calls` claim lands on a real
reference; a VIOLATED prohibition lands on the violation, which is the most
useful jump here.

With no evidence it falls back to the claim's own text, and a
`contains path:symbol` resolves its line through the SAME treesitter query
that decided |scry-verdicts|' `✓ defined` — a jump cannot land somewhere the
verdict did not mean. Failing that, line 1 of the file.

Nothing is invented. A prohibition that is holding names a pattern and not a
place; a claim whose file does not exist yet is the normal state of work not
yet done. Both say so instead of jumping somewhere plausible.

The jump does not take the glass's own window — the point is to have the map
and the code both in front of you. It reuses a window already showing
something else, and splits only when the glass is all there is.

THE HEADER is the window bar, so it stays in view from anywhere in a long
map rather than only from the top. It was virtual lines above line 1 until
Neovim was asked to draw them: there is no room above a buffer's first line,
so the counts were invisible on exactly the map a new user opens first. One
line now, with Vim's truncation point after the feature counts — a narrow
window gives up the claim-level evidence first and shows `<`, which reads as
cut off rather than as absent.

FOLDING is per feature: everything under a feature, prose and claims alike,
belongs to it. Lines above the first feature fold into nothing, so a
drafting block (|scry-drafting|) or a stale header is never swallowed.

THE MAP ARRIVES CLOSED. Features are what you scan; their members are what
you open one FOR, and fifty claims in view at once is the same wall of
detail the altitude work was about, rendered instead of authored.

The closed map KEEPS ITS COLORS. A folded line is normally drawn in one
highlight, so the whole thing came out a single gray — most of what a reader
looks at, in the one color that says nothing. 'foldtext' returns highlighted
chunks instead, so the name, the state and the count render as they do when
the fold is open and the state column can be read by color before it is read
by word: amber is building, cyan is unread, green is done, red is broken.

It is one feature per row, and built to be read as a column: the states line up at a common cell, so they can be run down rather
than hunted for. Each row drops the `feature` keyword, which repeated eight
columns down the page and told a reader nothing they could not see, and
carries the state and a MEMBER count — how much of the product the feature
is made of, where a line count would only measure how much prose someone
wrote about it. `fillchars` drops the fold's dot leader, which at this
density was eighty columns of noise per row on a page whose whole job is a
quiet list.

==============================================================================
HOW THE MAP READS                                                  *scry-lint*

|:ScryLint| reads the feature NAMES and flags the ones whose shape makes a
map hard to read. It asks the code nothing. Nothing it reports is a verdict
and nothing is rewritten — the map is a document you wrote, and how it is
worded is yours.

The rules come from the Quality User Story framework (Lucassen, Dalpiaz, van
der Werf and Brinkkemper, Requirements Engineering 21(3)), which defines
thirteen criteria for how a requirement is written and validates them
against 1023 user stories from eighteen companies. Four are checked here:

    atomic    The name joins two goals with `and` or `or`. This is the one a
              drafted map breaks hardest — six of eleven on a real pass —
              and it is why rows grow long enough to read as a wall. A row
              that is two things cannot be finished, ratified or scanned.
    uniform   The name does not start with a verb. A feature is what someone
              DOES; Cockburn's rule for naming a use case is an active-verb
              goal phrase, and eyetracking on scanning says the first word
              is the one that gets read.
    minimal   The name is long enough to have become prose. The detail
              probably belongs in the description beneath it.
    unique    Two names read like one capability. Exact repeats cannot occur
              — naming a feature twice re-opens it, |scry-reopening| — so
              what is left is two names for one thing, which is the failure
              that took one map to 301 features over 60 files.

WHAT IT DOES NOT CHECK, and why. Three of the framework's criteria —
`problem-oriented` (the name states the problem, not the solution),
`conceptually sound`, `unambiguous` — need understanding rather than
parsing. The framework's own tool draws the line in the same place and for
the same reason. So a name that encodes its mechanism passes here. That is
honest rather than complete, and a linter that guessed at meaning would be
wrong often enough to teach you to ignore it.

IT PREFERS A FALSE FLAG TO A MISSED ONE. "Accept the terms and conditions"
is one noun and gets flagged anyway. A finding says "if both halves are
things a person does" rather than "this is wrong", because glancing at a
wrong flag costs less than never seeing a real one.

==============================================================================
PROGRAMMING A CAPABILITY                                        *scry-compose*

Vim's bargain is an operator applied to a precisely addressed noun: `d2w`,
`ci"`, `>ap`. Conjurer ported that to generated edits — `~{motion}` rewrites
a region toward an intent. |:ScryConjure| raises the noun.

The thing you aim at is a FEATURE, and its address is every file the
feature is made of. Put the cursor on one, press `~`, say what you want,
and the change lands across the whole footprint. You do not open the files.
That is the point: a capability spanning four files is one thought, not
four.

ONE CAST, NOT ONE PER FILE. |:ScryCascade| does the other thing — it seeds
a claim's site into the quickfix list and lets conjurer visit each one with
the same intent. That is cheaper and reviewable a site at a time, but no
single request ever sees the whole capability, and a change that has to
stay coherent across files is exactly the change worth making here. A page
and the endpoint it posts to have to agree.

ADDING A CAPABILITY IS THE SAME VERB. A member's address comes from its
kind's probe, so `route print` names src/pages/print.astro whether or not
anything is there yet. Write the feature you want with the members it
should have and cast: absent members are files to create, present ones are
files to change.

A cast may only edit files it was shown. A path the model invents is a path
nobody addressed; it is refused and named, not written.

REVIEW IS VIM'S. Results land in BUFFERS, modified and unsaved — nothing
touches the disk. That is the state you would be in had you typed the
change yourself, so every tool you already have applies: `u` to undo a
buffer, `:diffthis` against what is on disk, `:w` what you keep, `:e!` what
you don't, `:wa` when it is all right. A review UI invented here would be
worse than the one already in your hands.

11. CONFIGURATION                                         *scry-configuration*

setup({opts}) is optional. Defaults: >lua

    require("scry").setup({
      -- The belief map, versioned with the code it describes.
      map_path = ".scry/map.scry",

      -- Where never-claims live. Empty = outside the repo, under
      -- stdpath("state"), so a repo-reading generator never sees them.
      -- An in-repo path shares them with your team and forfeits that.
      holdout_path = "",

      -- Claim-checking engine. Empty = treesitter + ripgrep (lua-first).
      resolver = "",

      -- How to run ONE spec for `exercises` claims: the spec's path is
      -- appended, and exit 0 means passing. Nothing here runs on :Scry —
      -- only on :ScryExercise. Left empty, exercises claims render "– unrun",
      -- which is honest: scry would rather say it does not know than guess
      -- your project's test command.
      test = { cmd = {} },   -- e.g. { "nvim", "--headless", "-u", "NONE", "-l" }
    })
<
                                                        *scry-project-config*
PER-PROJECT ~

Some of the above describes YOU and some describes THE REPO. A repo may carry
`.scry/config.json`, and exactly four keys are honored from it — the ones
whose right answer is a property of the project rather than of you:
>
    {
      "sources": ["lua/**/*.lua", "plugin/*.lua", "tests/*_spec.lua"],
      "test": { "cmd": ["nvim", "--headless", "-u", "NONE", "-l"] },
      "resolver": "",
      "map_path": ".scry/map.scry"
    }
<
The project wins for those keys, because it knows things your vimrc cannot.
Unknown keys are ignored without complaint, so a newer scry writing a key
this one has never heard of does not break it.

`map_path` is honored while `holdout_path` is refused, and that asymmetry is
deliberate: moving a file that is already committed changes nothing about who
can read it, whereas the holdout's entire value is being unreadable.

|:checkhealth| reports the config in effect here, project keys included — it
is where you go to find out what scry thinks, so a `sources` the project has
already overridden would send you to change the wrong setting.

Two keys are REFUSED, and the refusals matter more than the permissions:

`holdout_path` — the holdout lives outside the repository so that a
repo-reading generator cannot find it. A committed file able to relocate it
back INTO the repo is exactly how you would defeat that: hand someone a
project that quietly publishes its own prohibitions. Refused, and the refusal
is announced rather than silent.

`author` — describes a person, not a repo. Not a live config key today (the
trail replaced stamping), but refused rather than merely unknown, so a repo
still cannot sign your name if it ever returns.

JSON rather than Lua deliberately. Executing code out of a checked-out
repository is what Neovim gates behind |exrc|, and scry has no business doing
it silently for a config file.

12. HIGHLIGHTS                                               *scry-highlights*

Highlighting never claims more than the parser does. Grammar is colored
only inside a feature, because |scry-map|'s parser skips every line before
the first `feature` — a `contains` above it opens no section and the line
under that is not a claim. Both render as prose, which is what they are. A
syntax file that disagreed would be worse than none: it would tell you a
line was checked when nothing would ever check it.

Every group is a `default link`, so a colorscheme that defines any of them
wins outright. Verdicts borrow the DIAGNOSTIC groups, because a verdict is
the same kind of thing a diagnostic is and your scheme has already made
those readable. The buffer's own text borrows SYNTAX groups, because the map
is a language and reads best colored like one.

THE PAGE ~

                        separators, the timestamp. Default: Comment.

                        The bar is deliberately almost colorless: the counts
                        it holds are STATES, and they carry the same groups
                        the state column does, so a glance at the color says
                        what a glance at the words would. Painting the whole
                        line one color spent the scheme's loudest hue on the
                        words "scry" and "checked".
                                                            *hl-ScryEvidence*

is not decoration here — it is the difference between a strip of states you
can run your eye down and annotations you have to go and find.

13. WHAT SCRY DOES NOT CLAIM                                    *scry-honesty*

Every line here is a limit scry intends to keep stating plainly.

- **"backed" means accounted for, not correct.** The ladder is claimed →
  backed → exercised. v0 tops out at backed. Nothing scry renders is
  evidence that your code *works*.
- **`contains ✓ defined`** asserts a definition with that name exists in
  that file. It says nothing about its body. The prose above it is
  unchecked.
- **`contains ✓ present (file)`** asserts only that the
  file is there. Not that it does anything, not that the feature is
  implemented in it — the claim never said more than "this file is part of
  this feature", and the label is where that thinness has to show, because
  the feature rollup counts it like any other satisfied claim.
- **`calls ✓ referenced (text)`** asserts the token occurs in the feature's
  files and the target exists somewhere. It is NOT a resolved call: not
  reachability, not the same symbol, not proof the call happens. Rung:
  referenced < resolved < exercised.
- **`never ✓ no matches (rg)`** asserts no textual match. It is not absence
  of behavior — `local ui = vim.ui; ui.input(...)` defeats it. The
  asymmetry matters: a VIOLATED prohibition is proof, and carries the line
  that proves it; a clean prohibition is evidence.
- **`exercises ✓ passing`** asserts a spec process exited 0, at a stated
  time, with nothing it depends on having moved since. It is not proof your
  feature works — only that whatever that spec checks, held. A spec that
  asserts nothing passes just as loudly.
- **A named assertion is a weak check.** `spec.lua:some label` verifies the
  label appears in the spec's source and the file passes. It is NOT proof
  that assertion ran, or that it is the reason the file passed. scry cannot
  see inside a run; it sees an exit code.
- **An exercised claim is NOT held out the way a prohibition is.** A
  never-pattern can live outside the repository; a spec cannot — it has to be
  in the tree to run. So the guarantee is request-level only: scry never puts
  a test's path or text into what it hands a conjurer. A generator that reads
  your repository will find the test. See |scry-holdout| for why that
  distinction is kept sharp.
- **Verdicts describe saved files at a moment.** Unwritten buffers and edits
  made after the check are invisible. The timestamp travels with the render.
- **Holdout independence is against leakage, not adversaries.** See
  |scry-holdout| for the two guarantees and which is which.
- **Divergence is file-level and blunt.** A file a feature uses but never
  names reads as unclaimed, and what counts as a file at all is `sources`.
  It answers "is anything undescribed", not "is the description good".
- **A feature's state is only as good as its claims.** `✓ done` means every
  claim under it holds and someone here has read it — not that the feature
  works.
- **The trail is per-machine.** Ownership events live in local state, like
  run results — a teammate's glass shows their own trail, not yours.
- **`– unchecked` is not a pass.** A language with no resolver renders as
  unchecked, deliberately, so silence never looks like agreement.

==============================================================================
14. HEALTH                                                       *scry-health*

`:checkhealth scry` reports: Neovim version, ripgrep and the lua treesitter
parser (the resolver's two legs), where your map is and how many claims it
holds, where the holdout lives — warning if it sits inside the repo — whether
conjurer.nvim is installed (an ERROR when missing — it is required), and
whether quickfix-pro is present.
