i.
Understanding is the artifact
You write what the thing does — in prose, at the altitude you actually think at. The checkable lines underneath keep the prose honest. If you can't state it, you don't know it yet, and that's the useful part.
ii.
A change is a claim that isn't true yet
Write the line for what you want. It comes back ✗ absent. Nothing has broken — that's your worklist, stated in the same vocabulary as everything already there.
iii.
Conjure when the description is right
:ScryCascade hands it to conjurer with the concern as context. The code lands, the claim flips green, and you sign it. Not before you know what you're asking for.

Four rules

the whole design, in the order it matters
i. the split
Prose carries the thinking. Claims carry the check.
Write as much as you like — prose is kept verbatim and never checked. Claims are four indented forms: contains, calls, never, exercises. No parse errors; a line is a claim or it's prose.
ii. the seal
Editing a claim un-seals it. Mechanically.
:ScryRatify stamps a claim with your name and six hex of sha256 of its own text. Change the text and the hash stops matching, so it's unratified again. Signing means you understood it.
iii. the withheld rule
A prohibition the model never saw.
never claims are kept out of the repo and out of every request, then checked after the code lands. A rule shown to the generator proves nothing when satisfied — it was asked to. One it never saw is evidence.
iv. check before code
Conjure the test first, and hide it from the code.
Cascade an exercises claim, read the spec, confirm it goes red. Then cascade the contains claim — with the spec path withheld. Two generations from one sentence share its misreadings.

What the glass answers

every label says what was actually checked
✓ defineda definition node with that name exists (treesitter)
✓ referenced (text)the token occurs in the concern's files (ripgrep)
✓ no matches (rg)the prohibition found nothing
✓ passing (ran 4m ago)that spec exited 0, with its dependencies unchanged since
✗ absentnot there yet — usually your worklist, not a fault
✗ unreferencedthe target exists; this concern never mentions it
✗ VIOLATEDa prohibition matched — carries the line that proves it
✗ FAILINGthat spec exited non-zero — carries its output
∅ unratifiednobody has put their name on this claim
– uncheckedno resolver for this language. Not a pass.
– unrunnobody has run that spec yet. Not a pass.
– staleit passed, but the code has moved since. Not a pass.
– vacuous?it passes and nothing its concern claims exists yet. Not a pass.

A violated prohibition is proof, with its line attached. A clean one is evidence — no textual match is not absence of behaviour.

Five commands

zero config works · :h scry is the manual
CommandDoes
:ScryOpen the glass; check every claim.
:ScryCheckRe-check against the files on disk.
:ScryCascadeConjure the absent claim under the cursor, prohibitions withheld.
:ScryRunRun the specs behind exercises claims, then re-check. The only command that executes your code.
:ScryRatifySign the claim under the cursor.

What it won't say

a chapter of the manual, not a footnote
The map is written by you. scry does not recover it from the code — automatic architecture recovery tops out around half right.
Backed is not correct. claimed → backed → exercised. Nothing here says your code is right.
contains ✓ — a definition with that name exists. Nothing about its body.
calls ✓ — the token occurs and the target exists. Not a resolved call, not reachability.
never ✓ — no textual match. local ui = vim.ui defeats it.
exercises ✓ — a process exited 0, at a stated age. Not proof a feature works.
Verdicts describe saved files at a moment. Unwritten buffers are invisible.
Holdout independence is against leakage, not adversaries. Withholding a spec is weaker still — it lives in the tree.
The cascade seeds the file's first line. scry knows which file, not where in it. Placement is the model's call; the review is yours.
calls and never don't cascade. Neither has one obvious site to seed, and guessing beats refusing only rarely.
Know what you're asking for. Then ask.
